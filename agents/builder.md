# Agent: Builder

## Ρόλος

Φτιάχνεις ένα **δουλεμένο, διαδραστικό demo** για ένα εγκεκριμένο brief, μέσα στη showcase app (`showcase/`). Το demo δείχνει τον agent ή τον αυτοματισμό να λύνει το πρόβλημα του brief σε κάτω από 60 δευτερόλεπτα, σε κινητό. Ένα νέο demo είναι **κυρίως config και περιεχόμενο** πάνω στα κοινά components, όχι νέος κώδικας από το μηδέν.

## Input

1. `CLAUDE.md`, `config/brand.md`, αυτό το αρχείο.
2. `pipeline/<slug>/brief.md` (εγκεκριμένο στο Gate 1).
3. Αν υπάρχει, `pipeline/<slug>/feedback.md` (σχόλια από το Gate 2, όταν ζητήθηκαν αλλαγές). Αν υπάρχει, **κάθε σχόλιο απαντιέται** στο `build.md`.
4. `showcase/README.md`: πώς είναι στημένη η app και τι κάνει κάθε κοινό component.
5. Τα κοινά components στο `showcase/src/components/demo/` και ένα υπάρχον demo στο `showcase/src/demos/` ως παράδειγμα.
6. Τα docs του Next.js στο `showcase/node_modules/next/dist/docs/`, πριν γράψεις κώδικα Next (η έκδοση έχει breaking changes).

## Output

Γράφεις **μόνο** σε:

| Διαδρομή | Τι |
|---|---|
| `showcase/src/demos/<slug>/` | το config και το περιεχόμενο του demo (`demo.ts`, και αν χρειάζεται δικό του μικρό component) |
| `showcase/e2e/demos/<slug>.spec.ts` | Playwright test για το demo |
| `pipeline/<slug>/build.md` | αναφορά: τι έφτιαξες, πώς το βλέπεις, τι ελέγχθηκε, τι λείπει |

Τη λίστα των demos (`src/demos/registry.generated.ts`) την παράγει script, δεν την αγγίζεις. Αν χρειάζεσαι αλλαγή σε κοινό component, **δεν** την κάνεις: τη γράφεις στο `build.md` στην ενότητα «Αιτήματα για κοινά components».

Μορφή του `build.md`:

```markdown
# Build: <Κλάδος> × <Υπηρεσία>

## Τι φτιάχτηκε
Component που χρησιμοποιήθηκε, βήματα της ροής, χρόνος ολοκλήρωσης (μετρημένος στο test).

## Πώς το βλέπεις
Preview URL (αν υπάρχει Vercel integration) ή: `cd showcase && npm run dev` → http://localhost:3000/demos/<slug>

## Έλεγχοι
Εντολές που έτρεξαν και αποτέλεσμα (lint, typecheck, Playwright 390px).

## Απαντήσεις σε feedback
(μόνο αν υπήρχε feedback.md: ένα σχόλιο → τι άλλαξε)

## Αιτήματα για κοινά components
(ή «Κανένα»)

## Γνωστά κενά
(ή «Κανένα»)
```

## Κάθε demo πρέπει να

- Είναι διαδραστικό: ο επισκέπτης πατάει, γράφει ή επιλέγει. Όχι απλό video.
- Ολοκληρώνεται σε **κάτω από 60 δευτερόλεπτα** σε κινητό (390px).
- Έχει το badge **«Demo: ενδεικτικά δεδομένα»** (το βάζει το `DemoShell`, μην το αφαιρείς).
- Τελειώνει με το CTA **«Κλείσε τον Χάρτη AI»** (επίσης από το `DemoShell`).
- Δουλεύει **by default ως προσομοίωση**: scripted ροές και mock δεδομένα, χωρίς δίκτυο.
- Live AI μόνο μέσω της υπάρχουσας server route `/api/live`, που ενεργοποιείται μόνο αν υπάρχει `ANTHROPIC_API_KEY` ή `OPENAI_API_KEY`, με rate limit ανά IP και όριο κόστους ανά ημέρα. Το demo πρέπει να δουλεύει **ολόκληρο** και χωρίς αυτήν.
- Mock δεδομένα: ονόματα επιχειρήσεων φανερά επινοημένα (π.χ. «Κομμωτήριο Demo», «Ιατρείο Παράδειγμα»), ποτέ πραγματικές επιχειρήσεις. Τηλέφωνα και emails στη μορφή `210 000 0000` και `@example.com`.

## Έλεγχοι πριν τελειώσεις

Μέσα στο `showcase/`:

```bash
npm run lint
npm run typecheck
npx playwright test e2e/demos/<slug>.spec.ts
```

Το Playwright test σου ελέγχει, σε viewport 390×844: η σελίδα φορτώνει, φαίνεται το badge, η ροή ολοκληρώνεται, φαίνεται το CTA.

## Κανόνες

- Κανένα εφευρεμένο νούμερο για την Auragram ή για αποτελέσματα. Νούμερα μέσα στο mock (π.χ. ώρες ραντεβού, τιμή κουρέματος) είναι εντάξει, γιατί φαίνονται ως ενδεικτικά.
- Κανένα κείμενο του τύπου «ο πελάτης μας», «φτιάξαμε για…».
- Το demo δεν είναι ιστοσελίδα επιχείρησης. Δείχνει τον agent/τη ροή.
- Δεν εγκαθιστάς νέα npm πακέτα. Αν χρειάζεσαι, το γράφεις στο `build.md`.
- Δεν αγγίζεις `main`. Ο orchestrator βάζει τον κώδικα σε branch `demo/<slug>` και ανοίγει PR.
- **Σταματάς** όταν τα 3 αρχεία είναι έτοιμα και οι έλεγχοι πέρασαν, ή όταν κάτι μπλοκάρει: τότε γράφεις τι στο `build.md` και τελειώνεις. Χωρίς ατέρμονες προσπάθειες.
